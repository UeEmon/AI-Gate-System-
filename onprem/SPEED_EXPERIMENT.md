# Lipla速度改善の段階比較（Intel Mac Docker）

mainに統合した速度改善の段階比較機能です。
通常運用は基準のLipla方式のままです。比較はシステム性能画面から実行します。
比較候補は通常運用へ自動適用しません。Mac実機での速度・精度はこの画面で測定してください。

## 起動

リポジトリ直下で次を実行します。既存のデータ・モデルボリュームを保持します。

```bash
git fetch origin
git switch main
git pull --ff-only origin main
python3 onprem/setup_stream_receiver.py
docker compose --env-file onprem/.env -f onprem/compose.yaml -f onprem/compose.speed.yaml build gate
docker compose --env-file onprem/.env -f onprem/compose.yaml -f onprem/compose.speed.yaml up -d gate trainer rtmp-ingest
```

`compose.speed.yaml`は任意のOpenVINO依存をgateへ追加します。
ディスク容量が不足している場合は通常のcomposeのみで構築できますが、OpenVINO段階は未導入として失敗表示になります。
内部アダプターとの互換性を保つためLipla-jp 0.4.1を固定します。
既存キャッシュは保持しますが、モデル改訂で未取得ファイルがあれば初回ダウンロードされます。

Web画面 `http://localhost:8080` の「システム性能」→「Lipla速度改善の段階比較」を開きます。
ライブ監視・ファイル処理・学習・モデル比較を終了してから、同じ動画を一度アップロードしてください。
既定は先頭120フレーム、各設定2反復です。各設定のモデル初期化と先頭1フレームのウォームアップは測定から除外します。
先頭にプレートが映る動画で確認してください。warmup_ocr_callsが0ならOCRの実推論はウォームアップされていません。
最初は30フレーム・1反復で起動確認し、次に120フレーム・2反復へ増やしてください。
CPUで数秒/フレームの場合、全段階の測定には長時間かかります。各ワーカー上限は30分です。
「検証を中止」でワーカーを終了します。モデル初期化中は初期化が戻るまで中止に時間がかかります。

## 比較の段階

|段階|内容|
|---|---|
|基準|毎回YOLO→Liplaを実行|
|1: 車両追跡|保守的IoU追跡。98%以上で同じ番号が2回続くとOCR間隔を1秒に延長。未確定時は0.15秒ごとに再試行|
|2: フレーム選別|鮮明度・露出・サイズ改善時は早期再認識。低品質画像の再試行は最大0.4秒まで保留。初回認識は保留しない|
|3: CPU調整|PyTorchとONNX Runtimeを1・2・4スレッドで比較。ONNXの待機スピンを無効化|
|4: OpenVINO|同じYOLO重みのFP32・動的入力モデルをキャッシュへ変換。INT8量子化は行わない|
|5: 条件付きOCR|Lipla 0.4.1に限定。全体OCRの全4項目が98%以上かつ番号形式が有効なら項目別OCRを省略。低信頼度は従来の項目別OCRへ戻す。localプレートは従来処理|

段階3では正解評価で精度維持を確認した候補から95%遅延が最小のスレッド数を選びます。
正解なしでは暫定2スレッドです。段階5は段階4で精度維持を確認した場合のみOpenVINOを継承し、
それ以外はPyTorchのままで条件付きOCRの効果を比較します。
画面JSONのconfig・versionsで各段階の実行条件を確認できます。
OpenVINO未導入・非対応Liplaバージョン等は失敗表示とし、処理したふりはしません。

再利用したOCR結果は比較用ログにだけ出力し、新しい車両画像の教師データ・登録・通知には流しません。
外観変化・追跡の曖昧さ・追跡途絶では再認識します。
画像を飛ばすため、全フレームを認識した場合の絶対的な最高信頼度は保証できません。
定期再認識と鮮明度改善時の再認識で、より高い信頼度の結果への更新を継続します。

## 正解JSON

精度評価には、人が確認したフルフレーム上のプレート位置・ナンバーを指定してください。
frame_indexは0始まりです。空のplatesは「プレート無し」の正解として誤検出評価に使います。
任意のevent_idを同じ車両の一回の出現に付けます。省略時はナンバーをIDにします。
同じ番号の車両が再入場する場合は異なるevent_idにしてください。
枠は車両枠ではなく、画像全体に対するプレートの枠です。

```json
{
  "frames": [
    {
      "frame_index": 0,
      "plates": [
        {
          "event_id": "arrival-1",
          "box": [420, 300, 580, 380],
          "fields": {"region": "品川", "category": "300", "kana": "あ", "serial": "1234"}
        }
      ]
    },
    {"frame_index": 1, "plates": []}
  ]
}
```

正解は上限未満のフレーム番号にしてください。JSONは8MB以下、動画はWeb共通上限512MB以下です。
指定のないフレームの精度は評価しません。再利用した認識も含む検出継続率・番号完全一致率を測り、
新たに検出・OCRした割合をfresh_detection_fractionで分けます。
誤検出件数も集計し、一つの正解に複数の予測を割り当てません。
98%以上のLipla結果だけを正解とするとLipla自身の誤りを検出できないため、最終判定には手動確認済みの未使用動画を用いてください。
設定を調整する動画と最終テスト動画は分離してください。

## 結果の読み方

各段階のFPS・平均/95%フレーム遅延・車両検出/Lipla時間・OCR回数・CPU/メモリを表示します。
条件付きOCRの省略/フォールバック件数もJSONへ記録します。
CPUはLinux VM内のサンプル値で、macOS全体のCPU使用率とは異なります。取得不可はnullです。
ウォームアップ、モデルロード、OpenVINO変換時間はFPSから除外します。
FPSは前処理・推論・保存・通知キューまでの動画処理速度です。
外部AI・メール送信は検証で無効化し、運用データには書き込みません。
入力動画のデコードは含みますが、RTMP転送・カメラ側の遅延は含みません。

first_correct_by_eventには最初の正解ラベルフレームから最初の一致までの動画時間差と、
オフライン処理の経過時間を出します。実際のカメラ出現から通知までの遅延とは異なります。
正解を疎に付けると初回認識時刻の評価も疎になります。

精度維持は基準の検出継続率・完全一致率を下回らず、誤検出が増えない場合だけ表示します。
正解なしは未判定です。速度だけを根拠に運用へ自動適用しません。
各反復は独立したワーカー・追跡状態・出力DBで同じ先頭フレームを処理します。
比較終了・失敗・中止後には常駐モデルを元の設定に戻します。復元失敗はrestore_errorに表示します。

状態JSON: `/data/speed-experiments/state.json`
動画・段階別ログ・診断画像: `/data/speed-experiments/<run_id>/`
Webの「比較結果JSONを開く」で結果を確認できます。
入力・結果は検証領域に残るため不要になった検証ディレクトリは運用データとは別に削除してください。
検証中は共通計算ロックでバックエンド学習・比較・通常監視の新規開始を抑止します。
